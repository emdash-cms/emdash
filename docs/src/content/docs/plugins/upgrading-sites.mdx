This guide is for **site operators**: people who install plugins into a site. If you write plugins, see [Migrating to the plugin CLI](/plugins/creating-plugins/migrating-to-the-cli/) instead.

## Upgrade your dependencies

Update `emdash` and your plugin packages to their latest versions, then reinstall and rebuild:

```sh
pnpm up --latest emdash @emdash-cms/plugin-audit-log @emdash-cms/plugin-webhook-notifier @emdash-cms/plugin-atproto
pnpm build
```

After upgrading, your site may build and run without further changes. If the build fails or a plugin stops loading, work through the breaking changes below. Each one tells you exactly what to change.

For the full list of changes in each package, see its entry on the [releases page](https://github.com/emdash-cms/emdash/releases).

## Plugin KV storage when changing execution mode

`ctx.kv` data is shared between in-process (`plugins: []`) and sandboxed (`sandboxed: []`) execution for the same plugin ID.

Earlier releases stored non-`settings:` KV keys separately in each mode. Upgrading copies existing sandbox KV values into the shared store through a database migration. If a key already has an in-process value, that value takes precedence. The migration logs the plugin ID and key when the stored values differ, but does not log their contents. The original sandbox rows remain in `_plugin_storage` under the `__kv` collection for recovery; they are not read by the upgraded runtime. `settings:` keys keep their existing behavior.

The default runtime migration mode, `auto`, applies pending migrations and then starts plugins in the same startup. For this upgrade, apply migrations through the CLI **before starting the upgraded application**, so you can review conflicts before plugins write again.

<Steps>

1. Back up your database and stop all application instances and plugin jobs that write to it.

2. Upgrade `emdash` together with `@emdash-cms/cloudflare` or `@emdash-cms/sandbox-workerd`, whichever your site uses. Build the upgraded site, but do not start its server or deploy it yet.

3. Inspect the database target and apply migrations using the CLI from that build. Follow the [database migration guide](/deployment/core-migrations/#build-migrate-deploy-check) for target selection and credentials.

   ```sh
   pnpm emdash migrate --status
   pnpm emdash migrate
   ```

4. Resolve conflicting copies as described below, then deploy or start the upgraded site.

</Steps>

Mixed core/runner versions are not automatically rejected. Upgrading core alone copies a snapshot that an older runner can subsequently make stale; upgrading the runner alone can read the shared store before the backfill has run. Updating the other package later does not rerun a completed migration. Keep the packages together and all writers stopped throughout this procedure. Large KV backfills can exceed the runtime migration row limit, so they also require the CLI.

### Resolve conflicting KV values

If a plugin previously moved from in-process to sandboxed execution and saved new values there, its sandbox values may be newer than the in-process values. The database does not record enough information to determine which copy is current. Review conflicts before letting the upgraded plugin run, even if you missed the migration warnings. After plugins have resumed writing, differences can also be legitimate new shared values, not migration conflicts. Do not use the recovery UPDATE blindly on a running or previously restarted site: compare against the pre-upgrade backup and migration logs first.

The following query finds differing copies and shows both values. Run it in a private database console because plugin data may contain sensitive information.

```sql
SELECT s.plugin_id, s.id AS key,
       o.value AS shared_value, s.data AS sandbox_value
FROM _plugin_storage AS s
JOIN options AS o ON o.name = 'plugin:' || s.plugin_id || ':' || s.id
WHERE s.collection = '__kv'
  AND substr(s.id, 1, 9) <> 'settings:'
  AND o.value <> s.data;
```

If the sandbox copy is the one you want, restore that key while plugin writes remain stopped. The following query restores `config` for the `seo` plugin; replace those two identifiers with the plugin ID and key you reviewed. Do not restore every sandbox row blindly: the shared value may be the newer copy.

```sql
UPDATE options
SET value = s.data, revision = s.revision
FROM _plugin_storage AS s
WHERE s.collection = '__kv'
  AND s.plugin_id = 'seo'
  AND s.id = 'config'
  AND options.name = 'plugin:' || s.plugin_id || ':' || s.id;
```

### Roll back this upgrade

Older sandbox runners read the retained `__kv` rows, not the shared store. Downgrading packages alone hides writes made after the upgrade and can make deleted values reappear.

To roll back, stop the application and plugin jobs, save a separate backup of the upgraded database, and restore the pre-upgrade database backup together with the older application packages. Restoring that backup discards **all site changes** since the backup, not just plugin KV changes. If those later changes must be preserved, keep the upgraded runtime until you have prepared and verified a data migration back to the older storage layout.

## Breaking changes

### Changed: three first-party plugins use a default export

Earlier releases exposed first-party plugins as a named export and a factory call, for example `import { auditLogPlugin } from "@emdash-cms/plugin-audit-log"` used as `auditLogPlugin()`.

These plugins now provide a default export that you pass directly into `plugins:` or `sandboxed:`. There is no factory call. This affects `@emdash-cms/plugin-audit-log`, `@emdash-cms/plugin-webhook-notifier`, and `@emdash-cms/plugin-atproto`.

#### What should I do?

In `astro.config.mjs`, drop the braces around the import and the `()` after the plugin name.

The following example shows the change for `@emdash-cms/plugin-audit-log`, which runs in-process and goes in `plugins:`:

```js title="astro.config.mjs" del={1,7} ins={2,8}
import { auditLogPlugin } from "@emdash-cms/plugin-audit-log";
import auditLog from "@emdash-cms/plugin-audit-log";

export default defineConfig({
	integrations: [
		emdash({
			plugins: [auditLogPlugin()],
			plugins: [auditLog],
		}),
	],
});
```

Apply the same two edits to the other packages. `@emdash-cms/plugin-atproto` and `@emdash-cms/plugin-webhook-notifier` are sandboxed plugins, so they go in `sandboxed:` instead of `plugins:`; the import change is identical.

| Package                               | Default export binding |
| ------------------------------------- | ---------------------- |
| `@emdash-cms/plugin-audit-log`        | `auditLog`             |
| `@emdash-cms/plugin-webhook-notifier` | `webhookNotifier`      |
| `@emdash-cms/plugin-atproto`          | `atproto`              |

<Aside type="note" title="Where did the factory argument go?">
	The old factory call accepted per-install configuration. That configuration
	now lives in the admin UI, under the plugin's settings page.
	Set it there instead of in `astro.config.mjs`. There is nothing to pass at
	the call site, so the `()` is no longer needed.
</Aside>

This change applies only to the three packages listed above. Other native plugin imports may keep
their existing shape. For example, Field Kit remains `fieldKitPlugin()` under `plugins: []`; follow
each native plugin's installation instructions.

## After upgrading

If a third-party plugin still ships a named export and factory call, it has not been updated for this release. Check its changelog. All first-party plugins listed above use the default-export shape.
