This page is for contributors working on EmDash. It maps the main execution paths through the project. Site builders should read the user-facing [architecture](/concepts/architecture/) and [content model](/concepts/content-model/) pages instead.

[`CONTRIBUTING.md`](https://github.com/emdash-cms/emdash/blob/main/CONTRIBUTING.md) is the canonical source for repository layout and contributor workflow. [`AGENTS.md`](https://github.com/emdash-cms/emdash/blob/main/AGENTS.md) defines the code patterns and invariants that changes must follow.

## Astro integration

The `emdash` Astro integration resolves configuration during Astro's build hooks, adds Vite virtual modules, injects routes, and registers the request middleware. The integration does not copy route files into the consuming project.

Route injection is split by responsibility:

- Core admin, API, and public routes are registered in [`astro/integration/routes.ts`](https://github.com/emdash-cms/emdash/blob/main/packages/core/src/astro/integration/routes.ts).
- Configured authentication providers can add their own routes.
- Built-in passkey, OAuth, and magic-link routes are registered unless the site uses external authentication.
- The Model Context Protocol (MCP) route is registered unless MCP is disabled.

Use `routes.ts` as the route inventory. It contains the current path pattern and entrypoint for every core route, while [`astro/routes/`](https://github.com/emdash-cms/emdash/tree/main/packages/core/src/astro/routes) contains their implementations.

Virtual modules carry build-time configuration and statically resolvable extension points into the runtime bundle. Their identifiers and generated contents live in [`astro/integration/virtual-modules.ts`](https://github.com/emdash-cms/emdash/blob/main/packages/core/src/astro/integration/virtual-modules.ts). They cover configuration, database and storage adapters, authentication, plugins, media providers, admin extensions, and request-runtime helpers.

## Request pipeline

The integration registers middleware in [`astro/integration/index.ts`](https://github.com/emdash-cms/emdash/blob/main/packages/core/src/astro/integration/index.ts). A normal request passes through these responsibilities:

1. The runtime middleware initializes `EmDashRuntime`, selects the request-scoped database when required, and attaches the runtime to `Astro.locals`.
2. Redirect, setup, and authentication middleware handle routing prerequisites and resolve the current user. Playground mode supplies its own setup and authentication state.
3. The media-usage write fence protects collection changes while usage tracking changes state.
4. Request-context middleware exposes locale, preview, edit-mode, cache, and database context through `AsyncLocalStorage`.
5. The matched page or API route runs. API routes check authorization for the requested operation.

A configured outer middleware can wrap this pipeline. The exact registration order and playground conditions are defined by `buildMiddlewareEntries()` in `astro/integration/index.ts`.

## Runtime and data model

[`EmDashRuntime`](https://github.com/emdash-cms/emdash/blob/main/packages/core/src/emdash-runtime.ts) owns the database connection, schema registry, plugins, storage, and other services exposed to routes through `Astro.locals`.

Collection and field definitions are stored in `_emdash_collections` and `_emdash_fields`. Each collection has a corresponding `ec_<collection>` table with real columns for its fields. Content rows also carry publishing, revision, authorship, locale, and translation-group state.

Do not copy a column inventory from an early migration when changing this schema. The current shape is assembled from three sources:

- [`database/migrations/`](https://github.com/emdash-cms/emdash/tree/main/packages/core/src/database/migrations) upgrades existing databases.
- [`schema/registry.ts`](https://github.com/emdash-cms/emdash/blob/main/packages/core/src/schema/registry.ts) creates new collection tables and applies runtime collection and field changes.
- [`database/types.ts`](https://github.com/emdash-cms/emdash/blob/main/packages/core/src/database/types.ts) describes the database shapes used by Kysely.

When a schema change affects an `ec_*` table, update both the migration path for existing databases and `SchemaRegistry` for collections created after the migration.

## Content reads

Public content queries use Astro Live Content Collections:

1. `getEmDashCollection()` or `getEmDashEntry()` calls Astro's live-content API with the internal `_emdash` collection name and the requested collection type.
2. `emdashLoader()` resolves the request database and the corresponding `ec_*` table.
3. The loader applies collection, locale, publication, filter, ordering, and pagination rules.
4. Query helpers map the rows to Astro entries and hydrate related bylines and taxonomy terms.
5. Preview and edit-mode context can select draft data without changing the public query API.

The wrappers live in [`query.ts`](https://github.com/emdash-cms/emdash/blob/main/packages/core/src/query.ts), and the live loader lives in [`loader.ts`](https://github.com/emdash-cms/emdash/blob/main/packages/core/src/loader.ts).

## Admin and API writes

The React admin loads the manifest and uses TanStack Router and TanStack Query to call the injected API. The manifest describes the collections, fields, taxonomies, plugins, and other capabilities the admin can display.

API route files handle HTTP concerns such as parsing, authentication context, authorization, and response conversion. Business logic belongs in standalone functions under [`api/handlers/`](https://github.com/emdash-cms/emdash/tree/main/packages/core/src/api/handlers), which return `ApiResult<T>`. Repositories and services perform database work through Kysely, and plugin lifecycle hooks run around the operations that expose them.

## Extension and storage paths

Configured plugin descriptors are resolved at build time so native code, sandboxed code, admin extensions, and custom block components can be bundled for their intended runtime. Registry and marketplace bundles can also load from storage at runtime. [`plugins/manager.ts`](https://github.com/emdash-cms/emdash/blob/main/packages/core/src/plugins/manager.ts) coordinates plugin lifecycle and hook execution.

Media handlers use the configured `Storage` implementation through `EmDashRuntime`. Local storage and S3-compatible storage share the storage interface, while media providers add external browsing and rendering sources. Follow calls from [`media/`](https://github.com/emdash-cms/emdash/tree/main/packages/core/src/media) when changing upload, metadata, or rendering behavior.
